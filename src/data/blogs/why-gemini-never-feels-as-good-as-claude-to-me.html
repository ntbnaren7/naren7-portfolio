I don't think Gemini is a bad model. Quite the opposite, actually.

I've had some genuinely impressive experiences with Gemini. At one point, Gemini 3.8 Flash High was one of the models I genuinely enjoyed using for engineering. It could reason through complex problems, help me build substantial pieces of software, and sometimes solve things incredibly well.

But after using both Gemini and Claude extensively while building products end-to-end, I've noticed a pattern that keeps coming back:

When the problem gets genuinely complex, Claude feels like a better engineer to me.

Not necessarily a better code generator. A better problem solver. And that distinction matters.

The Real Test Isn't Writing Code

When I'm building a product, I write a lot of tests. Unit tests, integration tests, pipeline tests — whatever is necessary to make sure the system actually behaves the way I intended.

Because real engineering isn't:

Write code → run it → done.

It's:

Build → test → fail → investigate → understand → hypothesize → fix → verify.

The hard part isn't usually writing the first implementation. The hard part is figuring out why something broke. That's where I started noticing the biggest difference between Gemini and Claude.

When the Pipeline Breaks

Imagine you have a reasonably complex codebase. There are multiple components, dependencies, APIs, state transitions, tests, and architectural constraints.

You make a change. Your end-to-end pipeline fails. So you give the failure to an AI coding model and say:

"Figure out what's wrong and fix it."

There are two very different ways the model can approach that. One is:

Make the test pass.

The other is:

Understand why the system is failing.

They sound almost identical. They're not.

The Gemini Loop

One pattern I've repeatedly encountered with Gemini looks something like this:

It sees the error. It modifies the obvious piece of code. Runs the test. The test fails.

It modifies something else. Runs it again. Another thing breaks. Changes that. Runs it again.

And eventually, the process can turn into a loop of:

modify → run → fail → modify → run → fail.

The frustrating part is that the original objective can quietly change. You asked:

"Find the root cause."

But the model starts optimizing for:

"Make the current test pass."

Those aren't the same thing. Sometimes that can mean changing validation, altering assumptions, modifying mocks, restructuring logic, or making a local change simply because it makes the current failure disappear.

The code runs. Maybe the test passes. But the underlying problem may still be there.

At that point, the model isn't really debugging the system. It's reacting to symptoms.

Then Claude Does Something Very Different

I've given Claude the same kind of complex failures. And the first thing I notice is that it usually doesn't rush to modify the code. It investigates.

It looks at the file where the failure happened. Then it looks at the associated files. It traces the relevant pipeline. It reads the existing tests.

It runs the tests and looks at the actual failure. And only then does it start thinking about what could be causing it.

That sounds incredibly basic. But that's exactly how I expect an engineer to approach a difficult bug.

Symptoms vs. Causes

Suppose an error appears at the end of a pipeline. A shallow debugging approach asks:

"What line can I change to get rid of this error?"

A stronger approach asks:

"What assumption earlier in the pipeline caused this state to exist?"

That difference becomes huge when you're working on real systems.

Take Cognis, for example. Its architecture isn't just a single application function. There are multiple surfaces, event-driven components, cross-context communication, event contracts, and state flowing through the system.

If something fails at the end of that pipeline, the line throwing the error isn't necessarily where the actual problem is.

The same principle applied to the kind of reliability-focused work I was doing for the Razorpay Buildathon. When you're dealing with payment-related flows, recovery logic, state transitions, retries, and failure semantics, "make this test green" isn't enough.

You need to understand why the system reached that state in the first place.

Complex systems punish symptom-level debugging.

This Is Why Claude Feels Better

What I like about Claude isn't that it magically knows the answer. It doesn't. Claude makes mistakes too. What feels different is how it deals with uncertainty.

When it doesn't immediately know what's wrong, it tends to investigate the uncertainty instead of immediately trying random fixes.

It gathers context. It examines dependencies. It looks at the surrounding implementation. It checks the tests. It forms a hypothesis.

Then it changes something. And that change is usually connected to the hypothesis.

The workflow becomes:

Observe → understand → hypothesize → modify → verify.

Instead of:

Modify → run → fail → modify → run → fail.

The first one is debugging. The second can become trial and error. And when I'm engineering something seriously, I want the first.

And Yes, Claude Eats Tokens Like Crazy

Here's the funny part. Claude can be ridiculously expensive in tokens. Sonnet, Opus — doesn't matter. Give Claude a sufficiently complex engineering task and sometimes it will happily consume a mountain of tokens thinking through the problem.

And honestly? I don't care.

Because if those tokens are being spent understanding the system, tracing dependencies, reasoning about the failure, and arriving at the correct solution, that's a trade-off I'm perfectly willing to make.

I'd much rather have:

100k tokens of useful reasoning → one correct fix

than:

20k tokens → 17 code changes → 14 test runs → 6 broken assumptions → infinite loop.

So yes, Claude may be burning through tokens like it has absolutely no financial responsibility. But when it eventually looks at the problem, identifies the actual cause, makes the right change, and the entire pipeline goes:

boom — green.

I'll take it.

Gemini Was Actually Really Good

This is also why I'm not comfortable simply saying "Gemini is bad."

Because I've seen Gemini be really good.

There was a point where Gemini 3.8 Flash High genuinely surprised me with how well it could reason through complex engineering tasks.

It helped me build solid systems. It could understand problems. It could debug. It could reason about architecture.

And I remember thinking:

"Okay, this is actually really good."

Which makes the change I experienced afterward even more noticeable. At some point, that behavior became far less consistent for me.

The model started falling into the modify-and-rerun loop more often. Instead of investigating the failure deeply, it would sometimes keep trying increasingly local changes without really identifying what was fundamentally wrong.

I don't know why. Maybe the model changed. Maybe the inference configuration changed. Maybe the reasoning behavior changed. Maybe my workloads became harder.

I don't have enough evidence to say that Google "nerfed" anything. All I can say is that, from my experience, the quality of that engineering behavior changed. And that changed which model I trusted.

What I Actually Want From an AI Engineer

I don't want an AI that is obsessed with producing output. I want one that can stop and say:

"Wait. Something doesn't make sense here."

I want it to understand the architecture before changing it. I want it to inspect the tests instead of immediately assuming they're wrong. I want it to distinguish a symptom from a root cause. I want it to respect constraints.

I want it to understand that making one test pass isn't necessarily the same as fixing the system.

And most importantly:

I want it to optimize for correctness, not merely a green terminal.

Because that's what engineering actually is.

So, Is Claude Better Than Gemini?

I don't think that's really the right question. There are tasks where Gemini is excellent. There are tasks where Gemini may be the better choice. And I'm sure there are workloads where someone else's experience is completely different from mine.

Models change. Versions change. Inference configurations change. Tools change.

So I'm not claiming:

Claude > Gemini.

I'm saying something much narrower:

For the kind of complex, constraint-heavy engineering work I do, Claude has consistently felt more reliable at reasoning through failures and finding the underlying problem.

That's the difference I care about. Because writing a function is becoming increasingly easy for AI models. The harder problem is everything that happens when that function doesn't work.

The failing test. The hidden dependency. The incorrect assumption. The unexpected state. The regression. The architectural constraint. The bug that's actually three layers away from where the error appears.

That's where I start seeing the difference. And that's ultimately why, today, Claude feels better to me.

Not because Gemini is bad. Not because Claude is always right. But because when something breaks, I feel like Claude is more likely to stop, understand the system, reason through the failure, and then fix the actual problem.

And when you're building real software, that's the behavior I value most.

These are purely my own opinions and reflections. No AI was used to write any part of this blog.
